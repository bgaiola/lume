# Desktop packaging and signing (Phase 2 Block 5)

> Status: Block 5a (packaging pipeline) is complete and verified
> locally on macOS. Block 5b (real signing + notarisation) lights up
> automatically the moment the Apple Developer ID certificate
> activates and the secrets are added to the repository.

## What this block delivers

- A complete `tauri.conf.json` `bundle` section with platform-specific
  config for macOS, Windows and Linux. macOS hardened runtime is on,
  the entitlements file is referenced, the DMG layout is configured,
  Windows uses sha256 + DigiCert timestamping, Linux declares its
  WebKit / GTK runtime deps for both DEB and RPM.
- `src-tauri/Info.plist` with the `NSScreenCaptureDescription`,
  `NSAppleEventsUsageDescription`, `LSApplicationCategoryType`,
  `NSHighResolutionCapable` and `NSAppTransportSecurity` keys merged
  on top of Tauri's generated plist.
- `src-tauri/entitlements.plist` for macOS hardened runtime: JIT,
  unsigned executable memory, library validation disabled (Tauri /
  WebKit / Wry need all three), outbound network, dyld env vars.
  Audio + camera explicitly denied because Lume does not need them.
- A real macOS / Windows / Linux icon set generated by
  `pnpm tauri icon` from a single 1024x1024 source PNG. The
  `icon.ico` is now a true multi-resolution Windows icon, not the
  renamed PNG from Block 1.
- A `.github/workflows/desktop-release.yml` GitHub Actions workflow
  that builds on macos-14 (Apple Silicon), macos-13 (Intel),
  windows-latest and ubuntu-22.04. Triggered by tags matching
  `desktop-v*` or manually via the Actions UI. Publishes the
  artifacts as a GitHub release.

## Local build (no signing)

```bash
pnpm desktop:bundle
```

This runs `tauri build` from `apps/desktop`, which:

1. Builds `apps/web` for production (`pnpm --filter @lume/web build`).
2. Compiles the Rust shell in release mode.
3. Bundles the result into:
   - macOS: `.app` (under `target/release/bundle/macos/`) and `.dmg`
     (under `target/release/bundle/dmg/`).
   - Windows: `.msi` (Wix) and optionally `.exe` (NSIS).
   - Linux: `.AppImage`, `.deb`, optionally `.rpm`.

On macOS, without the Apple Developer ID env vars set, the resulting
`.dmg` and `.app` are **unsigned**. They run on the dev box (the
build host's user is implicitly trusted) but Gatekeeper rejects them
on customer machines with the "Apple cannot check this app for
malicious software" dialog. Distributing unsigned builds is a hard
no in production.

## Adding the Apple signing secrets (Block 5b)

Once your Apple Developer Program enrolment is active (look for the
"Welcome to the Apple Developer Program" email, takes up to 2 business
days), do the following on your Mac:

1. Open **Xcode → Settings → Accounts**, sign in with the Apple ID,
   click **Manage Certificates** and create a **Developer ID
   Application** certificate. Xcode generates a private key and
   stores both in the login keychain.
2. Export the certificate + key as a `.p12`:
   ```bash
   security find-identity -v -p codesigning
   ```
   Find the line that says `"Developer ID Application: <Your Name> (<TEAMID>)"`,
   copy the SHA1 thumbprint, then:
   ```bash
   security export -k login.keychain -t identities \
     -f pkcs12 -P "<a-strong-export-password>" \
     -o lume-developer-id.p12
   ```
3. Base64-encode it for GitHub Secrets:
   ```bash
   base64 -i lume-developer-id.p12 | pbcopy
   ```
4. Generate an **app-specific password** at <https://appleid.apple.com>
   (Sign-In and Security → App-Specific Passwords). This is what
   `xcrun notarytool` consumes; do NOT use your real Apple ID
   password.
5. In GitHub: **Settings → Secrets and variables → Actions → New
   repository secret** for each of:

   | Secret | Value |
   | --- | --- |
   | `APPLE_SIGNING_IDENTITY` | `Developer ID Application: <Your Name> (<TEAMID>)` |
   | `APPLE_CERTIFICATE` | base64 of `lume-developer-id.p12` |
   | `APPLE_CERTIFICATE_PASSWORD` | the export password from step 2 |
   | `APPLE_ID` | your Apple ID email |
   | `APPLE_PASSWORD` | the app-specific password from step 4 |
   | `APPLE_TEAM_ID` | your 10-character team id |

6. Push a tag (`git tag desktop-v0.1.0 && git push origin desktop-v0.1.0`).
   The workflow picks up the secrets, signs the `.app`, builds a
   signed DMG, runs `xcrun notarytool submit --wait`, staples the
   notarisation ticket, and publishes the release.

## Adding the Windows signing secrets (Block 5b, Windows side)

Windows hardening is more pragmatic than Apple's TCC story. Two
levels of trust:

- **Standard code-signing certificate** ($100-300/year, OV class):
  the `.msi` is signed and the SmartScreen warning attenuates over
  time as installations accumulate. Reasonable starting point.
- **EV (Extended Validation) certificate** ($300-600/year, hardware
  USB token): SmartScreen trusts the publisher from day one. Worth
  it once we have paying customers.

Both flows export the cert as a `.pfx` and feed it through
`signtool`. Tauri reads:

| Secret | Value |
| --- | --- |
| `WINDOWS_CERTIFICATE` | base64 of `.pfx` |
| `WINDOWS_CERTIFICATE_PASSWORD` | password protecting the `.pfx` |

The CI workflow already has the env vars wired; nothing else changes.

## Linux signing

Not signed in the traditional sense. The `.AppImage` ships
self-contained, the `.deb` and `.rpm` go through the user's package
manager which uses GPG signatures on the repository, not on each
package individually. If we ever publish to a Lume APT / DNF repo we
add a step here to sign the repository metadata.
